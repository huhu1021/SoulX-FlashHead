## 第四轮（16:07）：UI 重设计 + 口型同步模式

- **UI 重构**（VoicePanel.tsx + styles.css）：数字人舞台为左列主视觉（暗色影院渐变底、居中口型视频、状态徽章[待命/聆听/思考·口型生成中/回答]、呼吸光晕占位）；摄像头改为舞台右下角画中画（PiP）；右列为状态行+对话卡片；底部悬浮圆角控制条（.media-controls 全部更名 .voice-controls）。响应式 900px/720px 与暗色模式同步更新。
- **口型播放策略（前端）**：视频到达时若 agentState==='thinking'（同步模式、语音未出）→ 等进入 speaking 再播；否则立即播放（补播模式），旧段自动被新句替换，入场的 avatarIn 渐显动画。
- **口型同步模式（后端）**：FLASHHEAD_SYNC_MODE（config.flashhead_sync_mode，默认 false）——true 时 _speak_chunk 先 await flashhead.announce_and_wait(句)（视频生成+送达）再放行 TTS 音频，KB 直答路径音画对齐；代价：语音首包延迟≈3 倍音频时长（RTX 5070 Lite rf≈0.33）。omni 直答音频由实时模型直接出声无法延迟，两模式下口型均为补播。
- flashhead.py 队列改为 (text, Event|None) 元组，毒丸 None 不变；aclose 兼容。
- compose.yaml agent 环境加 FLASHHEAD_SYNC_MODE=${...:-false}（注意：变量替换读 shell/根 .env，不读 .env.local——开启需写入根 .env 或 compose 里改默认值后 up -d agent）。

- **双声音根因**：同一时刻两个语音会话并行（两个房间/两个 agent 进程，日志 08:26:52 同时收到两个 job，KB 查询雷同）——多个浏览器标签页同时开着语音会话各自收音播报。

- **大厂实时数字人调研结论**（客户要求首响≤1.5s 且不接受补播）：
  - 火山引擎 FlowAct-R1 实时互动数字人 API：单图建形象 + 16kHz 音频流 WebSocket/RTC 输入 → 声画毫秒级同步视频流（480P@25fps），首帧约 2s，明确支持自有 ASR/LLM/TTS 编排——架构匹配度最高；
  - 腾讯云智能数智人 IVH：首帧 <600ms 宣称，TRTC/WebRTC 接入，文本/声音驱动，通常商务开通且绑定其 TTS 方案；
  - 讯飞智作：宣称 ~250ms，语音驱动见长。
  - 延迟物理账：数字人开口=LLM首响(~1.3s)+视频首帧(2s/0.6s)，两者全达标需厂商首帧<0.2s 或接受音画同步优先牺牲首响。策略选择：音频立即播+口型恒定滞后 2s（语音达标）vs 音频缓冲对齐（声画同步、首响 3.5s）。
  - 待用户决策：厂商选择 + 开通服务拿 key；建议后端做 Provider 抽象（FlashHead/云厂商可切换）。
